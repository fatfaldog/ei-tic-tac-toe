# Design

## Context

См. proposal.md — Why. Настройки живут в `game.settings` движка (`{level, first, digitLayout, showDigits}`), применяются через `game.applySettings()` (валидация значений уже есть), запись — только `applySettingsOk()` в ui.js, старт — `UI.init()` создаёт `Game` и запускает первую партию. Спека «Автономная работа» требует работы с `file://`; localStorage в коде пока не используется.

## Goals / Non-Goals

**Goals:**
- Сохранение/загрузка четырёх настроек без изменения движка и разметки.
- Бесшумная деградация везде, где хранилище недоступно или испорчено.

**Non-Goals:**
- Сохранение состояния партии (поле, очерёдность) — только настройки.
- Кнопка «сбросить к умолчаниям» — отдельно, если понадобится.
- Перенос настроек между браузерами (экспорт/импорт).

## Decisions

1. **Мост в ui.js, движок чистый.** Две функции: `loadStoredSettings()` — читает и парсит, возвращает объект или `null`; `saveStoredSettings(settings)` — сериализует. Обе целиком в `try/catch` c feature-детектом `typeof global.localStorage === 'object'` (или try-доступом): доступ к `localStorage` в sandbox-iframe бросает `SecurityError` на самом обращении, детект свойства не спасает — значит try/catch вокруг каждого доступа.
2. **Ключ и формат.** Один ключ `krestiki.settings`, значение — JSON всех четырёх полей. Версионирования нет: при смене схемы старый мусор просто не пройдёт валидацию.
3. **Валидация переиспользуется.** Загруженный JSON подаётся в `game.applySettings()` до `newGame()` — движок сам отбросит некорректные значения (повреждённый ключ → умолчания, частично корректный → применятся корректные поля). Отдельный валидатор в UI не пишем.
4. **Точки записи/чтения.** Чтение — в `UI.init()` сразу после создания `game` (до первой `newGame()`): партия сразу идёт по сохранённым настройкам. Запись — в `applySettingsOk()` сразу после `game.applySettings(settingsDraft)`; отмена/черновик хранилища не касаются.
5. **Смоук: мок вместо повторного init.** `windowStub` получает простой `localStorage`-мок (объект-хранилище + `getItem`/`setItem`/`removeItem`). «Перезагрузку» эмулируем не повторным `UI.init()` (слушатели меню задвоятся), а прямой проверкой: после OK в моке лежит ожидаемый JSON; `loadStoredSettings()` (экспортируем для тестов как `NS.UI.loadStoredSettings`) читает его обратно. Недоступное хранилище: мок бросает/отсутствует → функции возвращают `null` и не роняют смоук.

## Risks / Trade-offs

- `file://`-хранилище различается по браузерам (Chrome/Firefox/Edge — работает, Safari — работает, но квоты/изоляция отличаются): деградация закрывает любой вариант; проверка на живом `file://` — в приёмке.
- Кросс-доменный iframe: современные браузеры партиционируют хранилище — настройки iframe'а не смешаются с сайтом-хозяином; sandbox без `allow-same-origin` — деградация.
- Пользователь вручную чистит хранилище — просто умолчания, консистентно со сценарием «повреждённые данные».
